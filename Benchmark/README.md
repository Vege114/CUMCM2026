# 无线电干扰源定位清除 Benchmark v1

本目录在编写基线运行报告之前，由独立子代理逐段阅读题干、两份附件和题目映射后建立。它将题目直接要求、实验诊断和内部验收约定分开，供以后修改模型时复用。题目没有公布总分公式、权重或平均时间合格线；本目录不构造“官方综合分”。

## 权威来源与指标选择

1. [题干](../docs/markdown/B题.md)：问题 1–4、附录 1–4；决定任务目标与必须交付的结果。
2. [附件 1](../docs/markdown/附件1.md)：第 1–2 节计时，第 4.3、4.6 节测试次数、案例真值与日志。
3. [附件 2](../docs/markdown/附件2.md)：第 1–5 节物理及协议，第 6–9 节响应，第 10 节计时样例，第 12 节程序注意事项。
4. [题目映射](../docs/problem-map.md)：交付位置导航，发生疑义时以前三份原文为准。

任务本质是未知源数、有限探测范围、带有界方位误差的主动感知与路径决策。Q3 的信号覆盖是圆盘；Q4 多了未知方向的半圆盘。机器人仅通过四个公开接口取得信息，不能读取官方案例位置、方向、半径或总数。先满足“确保全部清除”，再优化完成任务的虚拟时间；这是一种依据题意采用的内部比较顺序，不是官方评分排序。

## 官方要求的结果

| 字段 | 计算及来源 | 适用范围 | 比较方向与限制 |
| --- | --- | --- | --- |
| 测试案例编码 `case_code` | 模拟器界面/日志列表原值 | Q3/Q4 正式表格必填；演练建议保存 | 标识同一案例，不能据此读取真值 |
| 清除个数 `cleared_count` | 不同成功清除频道数；与 UI 结果核对 | 正式表格必填 | 更高更好，但不同案例总数不同 |
| 清除比例 `cleared_ratio` | `cleared_count / total_jammers` | Q3 演练明确要求；Q4 按相同条件检验 | 目标 1；正式测试真值不公开，必须留空 |
| 平均定位清除时间 `average_localization_clear_time_s` | `virtual_total_time_s / cleared_count`，秒/个 | Q3 演练、Q3/Q4 正式表格 | 先看全清，再看时间；清除为 0 时未定义，记 `null` |
| 程序运行时间 `program_runtime_s` | 成功 `/enter` 至测试结束的现实秒数 | Q3/Q4 正式表格必填 | 与虚拟时间分开；官方 UI 值优先 |

`virtual_total_time_s` 是题目平均时间的分子和实际优化目标，不是仅统计成功清除操作的耗时，也不是最后一个目标清除时刻。如果最后一个目标清除后继续排查，排查到 `/exit` 的时间也计入。题干定义未把耗时分配到单源，不应使用“逐源耗时均值”替代本式。

`total_jammers` 只允许来自演练结束界面或自建离线场景；HTTP 接口不返回总数。正式测试在任何界面也不显示真值。知道共 10–16 个不能推断“清除 10 个就完成”；演练或正式实验中未经证明的停止条件不等于全清保证。

## 时间核算与物理约束

对按执行顺序、按 `request_id` 去重的成功受理指令，记总移动路程为 `L`，合法检测次数为 `M`，检测频道切换次数为 `S`，清除尝试次数为 `C`，成功清除次数为 `K`：

```text
T_virtual = L / 5 + S × 1 + M × 5 + C × 3 + K × 2
```

初始位置 `(0,0)`，初始检测频道 `1`。移动由相邻 `/measure` 或 `/clear` 的位置推断。只有合法 `/measure` 更新检测频道，`/clear` 的频道只指定目标，既不切换频道也不产生切换耗时。`/enter`、`/exit` 均不增加虚拟时间。拒绝的请求不执行，响应中的 `virtual_time_s=0` 不能覆盖上一成功时钟；幂等重试只执行一次。

| 约束 | 题给范围/规则 | 应验证的实现行为 |
| --- | --- | --- |
| 源位置、频道和数量 | 半径 1800 m 圆域，20 个互异频道中选 10–16 个 | 不预知活动频道和总数；不把一个无信号观测当作频道不存在 |
| 机器人移动 | 直线、5 m/s；允许离开目标圆域 | 坐标有限、每分量绝对值 ≤ 2,000,000 m |
| 接收范围 | 每源有效半径 1000–1500 m | 不把 1500 m 当作保证检测半径 |
| 定向覆盖 | 方向两侧各 90°，含边界 | 定向无信号不能直接剔除源所在的整个圆盘 |
| 角度 | 从东逆时针 `[0,360)`，误差 ±1°，两位小数 | 正确跨越 0°；同点重复测量误差不独立 |
| 近距离检测 | 距离 ≤ 5 m 且有覆盖时返回 `near` | 不读取缺失的 `svd_deg`；可以直接清除 |
| 精确定位/清除 | 距离 ≤ 20 m，方向不影响成功 | 光学定位 3 s，成功再加 2 s；重复清除失败 |
| 现实时间 | 接口开放后 25 min 窗口；`/enter` 后最多 20 min | 实际预算以 `remaining_real_duration_s` 为准 |
| 虚拟时间 | 360,000 s 上限 | 留退出余量，标注超时/异常结束 |
| 协议 | HTTP 200 且 `accepted=true` 才算执行 | 动作串行；新动作新 ID；重试原内容和 ID |
| 日志 | 正式加密文件 ≤ 2 MB 才能上传 | 导出原文件名、内容不修改；保存客户端独立日志 |

角度两位小数带来的最多 0.005° 量化裕量可以作为实现的保守数值假设，但不是扩大官方误差定义。若采用该裕量，写入算法配置以保证比较一致。

## 逐问题验收标准

### 问题 1：几何正确性

需要给出由检测点及其示向度构造交会多边形的方法、区域直径算法，并回答同一直径的圆能否覆盖该区域。对有界非空凸多边形，直径等于最远顶点对距离；可以用两两顶点距离作为低复杂度基准答案。算法应说明复杂度，并显式处理空区域、单点、线段、近乎平行/无界情况，不能把数值裁切产生的边界误称真实定位边界。

用边长 `d` 的正三角形可验证“总存在直径为区域直径的覆盖圆”这一命题为假：其区域直径为 `d`，最小覆盖圆半径为 `d/sqrt(3) > d/2`。因此仅凭定位区域直径 ≤ 40 m 不能保证任选一个点在 20 m 内清除；实际清除点应有最大距离 ≤ 20 m 的覆盖证据。最小包围圆半径、顶点覆盖检查属于诊断/验收指标，题目没有指定其评分权重。

### 问题 2：第二检测点

需要明确“较好定位效果”的自选量化准则、可执行选择算法、第二点候选区域。可报告两次观测后区域直径/最小覆盖圆半径、第二次得到信号比例、附加移动耗时和交会角；这些都是内部诊断，不能标为官方评分项。候选区域应考虑首测 ±1° 扇区、源目标圆域、未知接收半径和第二点确实接收到信号的条件。对随机误差采用何种分布属于建模假设；仅有误差界并不意味着误差均匀独立。无信号回退策略须能运行。

### 问题 3：全向源

需要自动发现、定位、清除及可解释的停止条件，覆盖 10–16 个未知源。至少报告每次演练清除比例和平均虚拟时间。初版跑通一次是运行验收，不能替代充分演练或证明所有允许场景都可清除。论文最终还需要三次正式结果和三份原名加密日志；演练、自建模拟结果不能填入正式表格。

### 问题 4：混合源

在 Q3 基础上处理未知定向源数量、方向及 180° 覆盖导致的探测盲区。至少包括圆域边界处朝外发射、首次全频道无信号/少量信号、定位途中失去覆盖等压力场景。仍需三次正式测试和相应日志。只运行 Q3 不构成 Q4 验证；自建场景通过只能证明该测试集合上的效果。

## 初步测试集合

[scenarios.json](scenarios.json) 给出几何单元验收、协议计时验收、全向/混合场景分层和真实模拟器烟雾测试定义。`status="planned"` 表示规范定义，绝不表示已经通过。自建场景与官方演练分开统计，自建源分布/误差生成规则、种子、版本必须记录。官方测试随机生成，文档没有同一案例重放或固定种子的承诺，不应宣称跨版本官方结果是配对实验。

建议以后每版固定运行同一离线种子集合，分 Q3/Q4 和源数分层；再增加官方演练核验。每组报告样本数、全清场景率、清除比例、每场平均时间均值/中位数/最大值。`sum(T)/sum(K)` 是跨场按清除数量加权的指标，必须注明“汇总平均”，不能与 `mean(T/K)` 混淆。零清除和失败场景必须保留，不能通过删除失败案例美化时间。

## 评价器接口与结果管理

原始运行文件建议跟代码所在实验目录保存，本目录只管理长期规范和评价器：

```text
<实验目录>/runs/<run_id>/
  events.jsonl     # 每个请求尝试的客户端记录；不要包含登录凭据
  metadata.json    # 案例来源、配置、版本、结束 UI 真值
  metrics.json     # 本评价器输出
  ...             # 该运行的轨迹、图表和报告
```

```powershell
python Benchmark/evaluate.py --events <实验目录>/runs/<run_id>/events.jsonl --metadata <实验目录>/runs/<run_id>/metadata.json --output <实验目录>/runs/<run_id>/metrics.json
python -m unittest discover -s Benchmark -p "test_*.py"
```

每条 JSONL 至少含 `path`、`request`、`response`，建议同时提供 `http_status` 和 `client_elapsed_s`。`request` 保留位置、频道、`request_id`，将 `robot_id` 替换为 `REDACTED`。未形成响应的网络尝试可以将 `response` 设为 `null`。事件必须是单次运行，按客户端顺序记录，不能把多个会话混合。

元数据最小字段为 `run_id`、`problem` (3/4)、`mode` (`practice`/`formal`/`offline`)、`source` (`official_simulator`/`local_mock`)、`case_code`、`total_jammers` (未知用 `null`)、`total_source`、`algorithm`、`config`、`git_commit`。可增加 `program_runtime_s` 与 `program_runtime_source="simulator_ui"`、`official_cleared_count`、`final_virtual_time_s`、`end_reason`、`ended_at`、`simulator_version`、`seed` 和 UI 截图路径作为证据。自建场景不能使用 `source="official_simulator"`。

输出包括 `official_metrics`、`diagnostics`、`time_breakdown_s`、`clearance_timeline`、`validation` 和 `comparison`。`program_runtime_s` 无 UI 值时使用成功 `/enter` 与 `/exit` 响应的服务端时间戳差，来源标为 `server_timestamp_proxy`；它是近似证据，不应无说明抄入正式表格。没有结束响应或权威结束元数据时，总时间和平均时间保持 `null`，另报已观察到的时间下界。完整日志以 `/enter`、`/exit` 和时钟复核共同判断。`validation.valid_run` 只表示已记录协议/计时检查通过，不代表全清或策略得到数学保证。

比较优先展示清除率和 `all_cleared`，其次平均虚拟时间，并标注现实时间、场景来源和样本量。建议图表：清除率柱图、虚拟耗时分解堆叠图、累计清除数—虚拟时间阶梯图、路线图，以及后续同种子版本对比图。图表必须显示秒/分钟、比例分母和缺失值，不能把缺失率画成 0。

## 初版限制

本目录不运行官方模拟器、不读取官方案例隐藏数据、不消耗正式次数，也不填写未发生的正式结果。评价器使用公开接口日志重建执行结果；若动作执行后响应永久丢失，客户端不能独立恢复其全部效果，必须保留异常标记并用结束 UI 核对。精确位置误差、定向源分组清除率只能在有合法离线真值的自建场景中计算，不从官方模拟器隐藏数据推导。
